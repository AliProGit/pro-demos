6. The risk we cannot take

The production HCP patient list returns all patients of a program, with name, birth date, address, phone and e-mail, to any caller authenticated as the Heroku user.

Rule: the filtered class (TD-1793, in UAT and Pro Demo since 10/14) is deployed to production before any practitioner or staff member is invited. Luminopia Phase 2 (TD-1788) is the first date that matters.

What the fixed version does: requires an HCP identity (contact id, portal user id or NPI), returns only patients linked to that HCP through a case prescriber or servicing provider or an active patient-provider row, and never returns a roster.

8. What we do

One source of truth in the CRM; everything else derives from it.

Option A: Contact-Contact Relation as master

Already maintained by Ops (152 rows in prod), standard Health Cloud, visible on every contact page, has role and active flag. Missing: practice (derive from the doctor's account) and code that reads it.

recommended

Option B: Staff Physician Assignment as master

Read by the code and the deactivation flow, has practice, staff type and access level. Missing: no UI people use, no rows, and it asks Ops to maintain a second list.

becomes the mirror

  1. Mirror flow (davidb first). Record-triggered flow on Contact-Contact Relation: when one side is a Practitioner and the other is Office Staff, Clinical Staff, Practice Admin or Multi Site Staff, upsert a Staff Physician Assignment row (staff, doctor, practice from the doctor's account, staff type, active). One-time backfill of today's 152 prod rows. Existing code and the deactivation flow keep working.
  2. Fix the two readers. StaffPatientListResource takes a contact id instead of the logged-in integration user; ProSpectusPatientController gets its case query restored; both check the program.
  3. Deploy the TD-1793 HCP filter to prod before any practitioner is invited.
  4. LaunchPad Lab: write the assignment to the CRM when a practice admin makes it, and read the patient list from the CRM endpoints with the staff contact id. Drop the private copy.
  5. Clean-up: merge the two inactive Elizabeth Smyers duplicates; set Contact.AccountId on staff contacts without a practice; re-open TD-11 and TD-12 as new tickets.
  6. Fold into the access-model redesign (program-key sharing): this is the external half of "who can see which patient".

Owner: Ali for 1, 2, 3, 5; Ji and Carlos for 4; Ms. Reinhardt confirms A over B and the re-opening.
