Zip to Sales Rep: how a client's field team reaches a patient case

Journey demo for 2026-11-11. Synthetic examples. Counts are production metadata/row counts as of 2026-11-10 evening, no patient data.

One junction object answers one question

"For this program, in this zip code, who is the Sales Rep, the FRM, the ARM and the CTN?"

Client alignment fileOne row per zip: territory name, zip, city, county. Plus a people sheet: rep name, role, territory.
→
ContactsOne Contact per person. Record type = role (Sales Rep, FRM, ARM, CTN). Account = the client. Territory on the contact.
→
Zip to Sales Rep rowProgram + Zip + Territory. The trigger fills four lookups: Sales Rep, FRM Contact, ARM Contact, CTN Contact.
→
Enrollment caseCase is saved with a healthcare provider. Flow reads provider billing zip + case program, finds the row, copies the people onto the case.

Why zip + program, not address or territory

Territory names repeat between clients ("Dallas TX" belongs to many). Patients move. The provider's zip and the program are stable and already on every case.

Why one object

No separate FRM table, ARM table, CTN table. The same row that gives a rep gives the whole field team. Load once, read everywhere.

What the case shows

Sales Rep Contact, FRM Contact, ARM Contact, CTN Contact, Case Manager, and the zip row it came from, so anyone can audit the match.

Presenter: the question we are answering is "why was this FRM not on this case" and "is the rep on this case the right one". Everything that follows is the mechanics behind those two questions.

How client data gets loaded

Two screens in Salesforce, both already live. Azmath runs them when a client sends an alignment file.

Step 1. Contact importScreen proContactSalesRepComponent. Pick the client Account, upload the people sheet. Each row becomes a Contact with the role record type and the territory.
→
Step 2. Zip importScreen proZipToSalesRepComponent. Pick the Program, upload the zip sheet. Program is forced by the screen. Each row becomes a Zip to Sales Rep record.
→
Step 3. TriggerPROZipToSalesRepTrigger fires on insert and on territory or program change. Finds the contacts for program + territory, stamps the lookups.
→
Step 4. CasesTwo flows copy from the row to the case: Case - Update Case Manager (Case after save) and Associate HealthCare Provider - Update Related ZIP (after save on the HCP junction).

What happened today (2026-11-10)

A YcanthRx enrollment case showed an Invivyd sales rep and an FRM the team did not expect. We traced it.

1,356,464zip rows in production
1,069,840rows with blank zip AND blank program (79%)
14,601rows with a zip but no program (Nov 2025 load)
394cases linked to a program-less row
1 of 278territory values shared by Contact and Zip picklists

Bug 1. Case flows matched blank program

Both case flows look up the Program with a filter "Use Zip To Territory Mapping = true". YcanthRx had the flag off, so the lookup returned nothing, and the next query ran with Program = blank. That matched a legacy row for zip 23666 that carried an Invivyd rep.

Result: Invivyd rep on a YcanthRx case. 394 cases across 9 programs sit on such rows.

Bug 2. Trigger matched territory text only

The trigger took the newest Sales Rep contact whose territory text equalled the row's territory. No program or client check. "Dallas TX" for Client A could pick Client B's newest rep. It also only handled Sales Rep, never FRM, ARM or CTN.

Bug 3. Contacts and zip rows could not meet

Contact territory picklist has 29 values, zip picklist has 278, only 1 in common. The contact import also re-cased values ("Richmond Va"). Only 54 of 442 Sales Rep contacts even have a territory. The join almost never happened.

Data debt

Two bulk loads (May 2026 and 2026-11-10) inserted 1.07M rows with no zip and no program. They match nothing but they are 79% of the object and they make every report and list view lie.

What was NOT broken

The FRM answer itself. Zip 23666 and 23120 both belong to the Southeast FRM in the YcanthRx table. The FRM asked about covers the Northeast plus 25 Richmond zips. The bond worked; it just pointed at the right person, not the expected one.

Presenter: the "same program, same address" intuition is why this felt wrong. The key is program + provider zip, and Richmond VA is split between two FRMs at zip level.

What we built (fulluat, 2026-11-11)

Small, in the objects that already exist. No new object, no new integration.

Two case flows: one decision added

Program_Uses_Zip_Mapping. If the Program lookup found nothing, stop. The zip query can no longer run with a blank program.

Case - Update Case Manager v8, Associate HCP - Update Related ZIP v4.

YcanthRx flag turned on

PRO_Use_Zip_To_Territory_Mapping__c = true on YcanthRx Patient Support Services. The case flows now match its 41,558 zip rows.

Trigger handler rewritten

Program-aware: a contact matches when its Program equals the row's program, or its Account is the program's client account. Case-insensitive territory. All four roles: Sales Rep, FRM, ARM, CTN. No match = field left as loaded, never wiped.

Validation rule

Program_and_Zip_Required: Program and a 5-digit zip on every row, whatever tool inserts it. Stops the next 1M blank rows.

CTN Contact lookup + CTN role

New CTN_Contact__c on the zip row (filtered to CTN contacts). Contact import accepts role CTN.

Contact import keeps the zip spelling

Territory is validated against the zip table's picklist, case-insensitive, and stored with the zip table's spelling. No more "Richmond Va" vs "RICHMOND VA".

Zip import tells you what did not match

After the load, a yellow box lists each territory that got no Sales Rep / FRM / ARM / CTN, so the loader creates the contact and re-saves.

Tests

7 new handler tests: cross-client collision, program beats recency, case folding, no-match keeps loaded value, territory and program change, bulk 200. 26 tests green in the prod check-only validation.

Method

  • Facts first: every claim in section 3 is a query against production, counts and Ids only.
  • Fix the rule, not the record: no case was edited by hand.
  • fulluat first, prod check-only, prod deploy only with explicit go.
  • Every build script asserts its match count, so a silent no-op cannot ship.
  • Tests encode the three bugs: a collision test, a case-folding test, a no-wipe test.
Presenter: if asked "why not just fix the data", the answer is section 3 bug 1: the same flows would re-create the problem on the next program with the flag off.
